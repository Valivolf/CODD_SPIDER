# Бухгалтерский режим АПК

Роль `accounting` использует бухгалтерский режим `/apk`. Остальные роли используют
прежний технический интерфейс. Старый `/accounting` сохранён без перенаправления;
обе бухгалтерские страницы используют один список, общую карточку АПК из `point_card.js` и одни API.

## Поведение

- Основной список включает только АПК с хотя бы одним непустым бухгалтерским значением.
- «+ АПК» ищет существующий объект по основному и бухгалтерскому инвентарному номеру.
  Объект всегда выбирает человек, включая единственное совпадение. При дублях показываются
  все варианты с пагинацией, без автоматического выбора. В небольшом окне только два поля:
  название камеры и инвентарный номер. Кнопка «Добавить» сохраняет только эти значения
  для выбранного `point_id`, закрывает окно и обновляет список. Новая запись в `points`
  не создаётся. Если сведения уже есть, замена названия/номера требует подтверждения;
  остальные восемь полей сохраняются. Изменение номера сбрасывает выбранный объект.
- Номера сравниваются как строки без пробелов по краям и без учёта регистра; ведущие нули,
  внутренние пробелы и знаки сохраняются. Номер самого АПК не подменяет инвентарный номер.
- Поиск основного списка: номер АПК, бухгалтерское название и оба инвентарных номера.
  Название берётся из существующего поля «Наименование в бухгалтерском учете»; распознаётся
  также написание «учёте».
- Все десять существующих полей сохраняются в `point_category_field_values` через `point_id`.
  Основной инвентарный номер автоматически не меняется. Балансовая стоимость проходит через
  `Decimal` и сохраняется десятичной строкой без преобразования через JavaScript Number или float.
- После сохранения обновляются форма, версия и список. При ошибке ввод остаётся в форме.
  При конфликте можно увидеть актуальные значения; заменить свой ввод ими можно только явно.
- Список использует шапку, белый контейнер, кнопки и компактные плитки справочника `/apk`.
  Детальная карточка — существующая полноэкранная карточка администратора с разрешёнными
  разделами: «Основное», «Учётные и дополнительные поля», «Фото», «Файлы».
  Поля редактируются в прежних строках label/value и сохраняются кнопкой «Сохранить поля»
  без закрытия карточки. Год выпуска отображается как `2020`, включая старые значения `2020.0`.
- Адрес, координаты и номер АПК в бухгалтерском режиме доступны только для чтения.
- Фото и файлы используют существующие маршруты, форматы, ограничения и хранилища.
  Бухгалтер может читать и загружать вложения существующего АПК; новых прав удаления нет.
  Повторно используются галерея по дням, выбор даты фото, просмотр документов, скачивание,
  перетаскивание файлов и комментарий к загрузке из административной карточки.
- Обычные читатели карточек АПК видят бухгалтерские поля, но `points.edit` и даже отдельно
  присвоенное обычной роли `accounting.edit` не дают права их менять. Изменение бухгалтерских
  полей разрешено роли `accounting` и администратору при наличии `accounting.edit` / `*`.

## Выгрузка выбранных комплексов в Excel

В бухгалтерском списке доступны отметки отдельных АПК, «Выбрать все загруженные»,
счётчик выбранного, «Снять выбор» и «Экспорт в Excel». Выбор сохраняется при поиске
и подгрузке страниц; общий флажок действует только на загруженные строки текущего
результата, а экспорт включает весь выбор. Без выбранных записей кнопка отключена.
За одну выгрузку можно выбрать до 5000 комплексов.

`POST /api/accounting/export` принимает `point_ids` и требует `accounting.view`.
Он читает актуальные значения в одном снимке БД и формирует `accounting-apk.xlsx`:
одна строка на АПК, номер, адрес, широта, долгота и существующие бухгалтерские поля
(включая название и бухгалтерский инвентарный номер). Технические сведения в файл
не попадают. Если выбранный АПК исчез или все его бухгалтерские значения очищены,
сервер сообщает об этом вместо неполной выгрузки. Повторные ID не дублируют строки.

В Excel есть фильтры, закреплённая шапка и перенос длинного текста. Инвентарные и
заводские номера остаются текстом с ведущими нулями, даты и год имеют свои форматы.
Обычные денежные суммы выгружаются числами; суммы длиннее точности Excel (15 цифр)
или с более чем двумя десятичными знаками остаются точным текстом. Пользовательский
текст, начинающийся с `=`, не исполняется как формула.

Экспорт не изменяет БД. Новых зависимостей и миграций нет: используется существующий
`openpyxl`. Формирование файла выполняется вне основного цикла обработки запросов.

Проверка 17.11.2026: 18 серверных тестов прошли. Chrome проверил выбор, общий флажок,
снятие выбора, сохранение отметок при поиске, фактическое скачивание XLSX, а также
прежние сценарии карточек бухгалтера, оператора и администратора.

## Граница доступа

Бухгалтерский API выдаёт только разрешённые сведения и бухгалтерские значения.
Бухгалтерский интерфейс подключает общий `point_card.js` в ограниченном режиме;
не подключает модули подгрупп, проверки и карт и не вызывает API оборудования,
SIM, технической карточки, статусов, проверок, подгрупп и планов.

Общий `/api/points` для роли accounting также отдаёт безопасную проекцию. Прямые запросы
на изменение технической карточки и технические действия АПК блокируются на сервере.
Права других ролей и существующие складские разрешения accounting не сбрасываются.
Независимый доступ бухгалтерии к складу и операциям оборудования остаётся по прежним правам,
но бухгалтерская `/apk` эти данные и действия не использует.

Чтение и загрузка вложений бухгалтером дополнительно проверяют бухгалтерское разрешение
и существование связанного АПК; это относится и к скачиванию по прямому ID вложения.
Доступны существующие файлы АПК, как предусмотрено заданием; отдельная классификация
«секретный/бухгалтерский файл» не вводится.

## Версии и объединение

Подготовлено одно добавочное изменение схемы: `points.accounting_revision INTEGER NOT NULL DEFAULT 0`.
Оно включено в существующий идемпотентный `init_db` через `_ensure_column`.
Текущие значения, инвентарные номера и настройки ролей этой доработкой не мигрируются.

API чтения возвращает `accounting_revision`. При записи бухгалтерских значений клиент
обязан передать `expected_revision`; отсутствие или несовпадение даёт HTTP 409.
Проверка версии, сохранение всех значений и увеличение версии проходят в одной транзакции
`BEGIN IMMEDIATE`. Очистка всех полей также увеличивает версию.
Старые клиенты без версии не могут безусловно перезаписать данные — страницу нужно обновить.

Объединение переносит бухгалтерские значения до удаления дубля. Разные непустые значения
одного поля останавливают объединение с понятной ошибкой. Изменения всей группы в одном
вызове `merge` откатываются, включая ранее обработанные дубли. Пустые поля основного АПК
заполняются значениями дубля, одинаковые значения сохраняются. Версия основного АПК увеличивается.
Существующий пакетный API, как прежде, обрабатывает разные группы отдельными вызовами merge.

## Проверки

Серверные тесты запускаются из корня проекта:

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

Тесты подменяют настройки до импорта маршрутов, не читают `.env`, не импортируют `app.main`
и используют временную SQLite-базу и временные вложения. Проверяются 18 сценариев:
фильтрация, поиск, оба номера и дубли, отсутствие создания физического АПК, все поля,
денежная точность, конфликт параллельной записи, роли, технические запреты, порт,
объединение и откат, фото/файлы, обычное создание и редактирование АПК,
повторяемость схемы и сохранность ролей, переход со старой схемы без столбца версии,
стартовая страница и шаблоны; выгрузка выбранных АПК, типы ячеек Excel и права экспорта.

Браузерные проверки на Windows с установленными Node.js и Chrome/Edge:

```powershell
node tests/accounting_browser.cjs
```

Скрипт запускает скрытый Chromium с отдельным временным профилем и сервер только на
127.0.0.1 с тестовой БД. Проверяет добавление в два поля, отсутствие совпадений, дубли,
ручное подтверждение единственного совпадения, сброс выбора при изменении номера,
общую полноэкранную карточку, все десять полей и повторное открытие, год без дробной части,
конфликт с сохранением ввода, общую загрузку фото/файла с комментарием и их просмотр,
мобильную ширину, отсутствие технических запросов, старый `/accounting`, обычный интерфейс
оператора, сохранение бухгалтерских полей и редактирование адреса администратором.
Скриншоты можно сохранить, указав существующий каталог в `ACCOUNTING_SCREENSHOT_DIR`.
После завершения сервер останавливается и временные данные удаляются.

Проверка исправленного интерфейса 16.11.2026: все 16 серверных тестов прошли (28,917 с),
все четыре группы браузерных проверок прошли. Проверены скриншоты списков и карточек
accounting/admin, небольшого окна добавления и бухгалтерской карточки шириной 390 px.
Для этой UI-доработки серверный код и схема БД не менялись; дополнительной миграции нет.
Изменены `accounting.js`, `point_card.js`, `ui.js`, шаблоны `apk.html`/`accounting.html`,
два файла тестов и этот отчёт. Ранее подготовленный столбец версии по-прежнему необходим
при обновлении со старой серверной реализации.

Ограничение проверок: реальный рабочий сервер, сетевой фотоархив, интеграции и производственная
нагрузка не проверялись. Установочные `scripts/offline/selftest*.sh` обращаются к развёрнутым
службам и не запускались. На ограниченной Windows-среде asyncio/браузеру нужно разрешить
локальные соединения; это не требует доступа к рабочей базе.

## Обновление — только оператором после отдельного решения

Рабочая база и сервер в ходе реализации не изменялись, развёртывание не выполнялось.

1. Сохранить согласованную резервную копию БД, ключей и файловых хранилищ.
2. Проверить новую сборку на отдельной копии данных, включая пользовательские настройки ролей.
3. В согласованное окно остановить старый экземпляр и развернуть сервер и статику вместе.
4. При ручном запуске обновлённого приложения его обычный `init_db` добавит единственный
   новый столбец. Не запускать init_db отдельно против работающей производственной БД.
5. Обновить открытые вкладки. Проверить вход accounting, поиск и сохранение существующего АПК,
   просмотр обычным пользователем и редактирование администратором.

Нельзя оставлять старую и новую версии сервера одновременно пишущими бухгалтерские поля:
старый сервер не знает о проверке версии. Синхронизация двух инвентарных номеров,
массовое исправление старых денежных значений и изменения складских связей не выполняются.
